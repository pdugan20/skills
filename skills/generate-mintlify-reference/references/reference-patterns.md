# Reference page patterns

House conventions for generated reference pages. These sit on top of the official
`mintlify` plugin's component syntax; this file covers the editorial shape, not
the syntax.

## Parameters: `<ParamField>` over tables

Prefer `<ParamField>` for command options and tool parameters. Its type, required,
and default badges read better than a table, and descriptions wrap as paragraphs
instead of cramped cells.

```mdx
<ParamField path="--branch" type="string" required>
The pickup branch, as a 3-letter code or a case-insensitive name.
</ParamField>
```

Use a parameter **table** only inside generated MCP output where many tools each
have a few params and compactness wins (the `gen_mcp_reference.py` template emits
tables for this reason). Keep one style per page.

## Synopsis line per command

Lead each command with a one-line synopsis so the shape is scannable:

```text
<tool> <command> [OPTIONS] <ARGS>
```

## Per-domain split with an overview landing

Once a reference has more than a handful of entries, split it:

```text
reference/
  cli.mdx              overview landing: what the CLI is, links to each domain
  cli/library.mdx
  cli/playlists.mdx
  ...
  mcp-tools.mdx        overview landing
  mcp-tools/library.mdx
  ...
  configuration.mdx
```

Add the groups to `docs.json` Reference tab (CLI group, MCP group, plus
`configuration`). The overview landing is the only hand-touchable framing; the
per-domain pages are generated.

## The "From Claude" nudge

Reference and guide pages for a tool that also has an MCP surface get a single
one-line nudge linking MCP setup and the per-domain tool reference. Do not dump
tool names inline; the reference owns them.

## Generated banner and determinism

Every generated file starts with:

```mdx
{/* GENERATED by scripts/<name> — do not edit by hand. */}
```

Generators must be deterministic: sort commands/tools by name, collapse internal
whitespace, and avoid timestamps or machine-specific paths, so the drift check is
stable across machines.

## Drift CI

Add a Makefile target and a CI job. The job regenerates and fails if the
committed output changed, which forces the generator and the docs to stay in
sync.

Makefile:

<!-- markdownlint-disable MD010 -->

```makefile
# Regenerate the CLI + MCP reference from source. CI fails on drift.
docs-reference:
	python scripts/gen_cli_reference.py
	python scripts/gen_mcp_reference.py
```

<!-- markdownlint-enable MD010 -->

GitHub Actions (`.github/workflows/docs-reference.yml`):

```yaml
name: Docs Reference Freshness

on:
  pull_request:
    branches: [main]

jobs:
  freshness:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6.1.0
        with:
          persist-credentials: false
      - uses: actions/setup-python@ece7cb06caefa5fff74198d8649806c4678c61a1 # v6.1.0
        with:
          python-version: '3.12'
      - name: Install package
        run: pip install -e .
      - name: Regenerate reference
        run: make docs-reference
      - name: Fail on drift
        run: git diff --exit-code docs-mintlify/reference
```

## API reference: prefer Mintlify-native

For HTTP APIs, do not hand-roll a generator. Point `docs.json` at the OpenAPI
spec and let Mintlify generate endpoint pages and the playground. Use the
available Mintlify capability or current official documentation for the
`openapi` wiring. This skill only adds the house framing: an overview landing
page with a real `description` and `icon`, and the "From Claude" nudge where
relevant.
